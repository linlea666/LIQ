# 潜力币雷达

在币安钱包的公开榜单数据上做早期发现：找出**还没上热门榜、但已经出现真实资金与人群迹象**的 BSC / Solana 代币，发邮件提醒，并持续追踪它们后来到底涨到了哪里。

系统与 LIQ 主服务完全隔离——独立容器、独立数据库、独立端口，两者没有任何共享状态。主后端重启不会打断雷达正在追踪的代币生命周期，反之亦然。

---

## 这个系统的立场

在 meme 币这个领域，**绝大多数标的最终归零**。任何声称能稳定挑出赢家的系统都在自欺。因此雷达的设计目标不是"选出会涨的币"，而是三件更朴素的事：

1. **比热门榜更早注意到**——领先时间是它唯一真正的产出。等币安把它放上热门榜时，所有人都看到了。
2. **诚实地记录自己的判断有多可信**——每个评分都带着它的数据完整度。基于 30% 完整数据算出的"机会 87"和基于 95% 数据的"机会 87"是完全不同的东西。
3. **保留被自己拦下的样本**——一个只看自己发出的警报的系统会持续自我肯定，因为它永远看不见自己错杀的赢家。

第 3 点是最容易被省略、也最不该省略的。研究页存在的全部意义就是回答"我们的阈值是不是设错了"。

## 快速开始

### 本地开发

```bash
cd radar
python3.11 -m venv .venv
.venv/bin/pip install -r requirements.txt

cp .env.example .env      # 填入 SMTP_USER / SMTP_PASS
.venv/bin/python main.py  # 监听 :8000
```

前端在 `frontend/` 下 `npm run dev`，访问 <http://localhost:3000/radar>。

### 生产部署

```bash
cp radar/.env.example radar/.env   # 填凭据
./deploy.sh                        # 主后端 → 雷达 → 前端，串行构建
```

雷达在 `:8802`，控制台在 `:8801/radar`。

`./deploy.sh --no-radar` 会跳过雷达——主链路出问题时优先保行情大屏。雷达起不来**不会**阻断部署，但日志会打出来。

### 跑测试

```bash
cd radar && .venv/bin/python -m pytest tests/ -q
```

## 数据流

```
币安公开榜单 (6 类端点 × 2 链)
        ↓  调度器：分层限额 + 429 自适应降速
    采集器：解析 → 归一化 → 观测对象
        ↓
    注册表：按币合并多来源观测 → 评估
        ↓
    ┌── 数据质量：字段完整度 + 新鲜度 ──┐
    │   风险门：硬拦截 / 研究门         │
    │   特征引擎：速度、加速度、比率      │
    │   五维评分                       │
    │   状态机：滞回 + 最短驻留 + 退出确认 │
    └────────────────────────────────┘
        ↓
    警报：冷却 → 限速 → outbox → 邮件
        ↓
    追踪器：持续记录它后来涨到了哪里
```

### 六类数据源

| 端点 | 提供什么 | 频率 |
|---|---|---|
| Trending | 热门榜（**领先时间的基准线**） | 60s |
| Meme Rank | 榜单排名与涨跌 | 60s |
| Smart Money Inflow | 聪明钱净流入 | 60s |
| Social Hype | 社交热度 | 300s |
| Meme Rush | 新币/毕业中/已迁移 三段生命周期 | 60s |
| Token Detail / Audit | 持币分布、合约审计 | 按需 |

采集策略是**被动批量更新**：优先用列表端点一次拿回几十个币的数据，把稀缺的单币详情请求留给真正高价值的目标。

## 关键设计

### 不可变的决策现场

`alerts`、`snapshots`、`rejections`、`outcomes` 一律只增不改。唯一可变的列是 `alerts.review_state`——机器判断不可变，人的工作流状态可变，两者严格分离。混在一起会让"当时机器怎么判的"被后来的人工操作覆盖。

每条记录都带 `config_hash` + `code_commit` + `strategy_version`。半年后回头看一条警报，这三个字段是唯一能说明"当时那套参数到底是什么"的东西。

### 两层风险过滤

- **硬拦截**（`execution_blocker`）：蜜罐、无法交易、流动性归零。命中即完全排除。
- **研究门**（`research_gate`）：Top10 过度集中、创建者持仓过高等。不发警报，但**保留样本**——这些是反事实分析的原料。

区分两者的理由：硬拦截的对象是确定的骗局，留着没有研究价值；研究门拦的是"看起来风险偏高"，而这个判断本身可能是错的，必须能被检验。

### 三种峰值

追踪结局时同时记录三个数字，因为只看第一个会系统性高估：

- **原始峰值**：含瞬时插针。好看，但通常卖不到。
- **持续峰值**：剔除插针后的高点，更接近真实可卖出价。
- **流动性折算倍数**：考虑滑点后能实际落袋的。纸面 10 倍常常只有 3 倍。

### KPI 只统计成熟样本

一个昨天发出的警报还没走完 7 天窗口。把它算进 7 天 KPI 会系统性低估收益（右删失）。因此 `kpi_daily` 只统计已到期的样本，并且**必须同屏显示 `matured_count`**——3 个样本的 67% 和 300 个样本的 67% 不是同一个信息。

### 内存约束

容器上限 512MB，稳态约 150-250MB。控制手段：

- 注册表最多驻留 4000 个代币视图，按活跃度淘汰
- 历史缓冲用双 deque（近期密集 + 远期稀疏），2 小时覆盖但不线性增长
- 快照写入有最小间隔，状态未变时不重复落库
- 超过 400MB 触发 `MEMORY_WARNING` 事件——OOM Kill 不会留下任何日志，只会让服务无声消失

## 控制台

`:8801/radar`，七个页面：

| 页面 | 回答什么问题 |
|---|---|
| 指挥中心 | 现在值得看什么？系统本身可不可信？ |
| 扫描器 | 全量代币横向比较 |
| 警报 | 我们报过什么，它们后来怎么样了 |
| 研究 | 我们的阈值是不是设错了 |
| 运维 | 雷达自己有没有病 |
| 配置 | 不登服务器改运行参数（需管理令牌，重启生效） |
| 代币详情 | 单个币的完整档案：轨迹、警报、拦截、结局 |

界面上贯穿一条纪律：**任何数值旁边都要能看出它有多可信**。扫描器里"完整度"列紧邻"机会分"，视线扫过时必然经过它。

## 运维

### 健康检查

```bash
curl localhost:8802/api/radar/ready    # 降级时返回 503
curl localhost:8802/api/radar/health
```

`/ready` 的判据是"最近一轮确实采到过数据"，而不是"进程还活着"。一个所有接口都在超时的雷达在进程层面完全健康，但它已经不再是雷达了——如果它报告 200，编排层就永远不会重启它。

### 排障

```bash
curl localhost:8802/api/radar/diagnostics/bundle | jq
```

一次性抓取健康、调度、表体积、近期错误和待发邮件。分十次调不同接口再手工拼起来，每一步都可能拿到不同时刻的状态，最后拼出一幅并不存在的图景。

**症状对照**：

| 现象 | 先看哪里 |
|---|---|
| 最近没有新币 | `/diagnostics` 的 `rate_limited_total`。被 429 限流后会自动降频，表现和"真的没有新币"完全一样 |
| 有警报但没收到邮件 | `email_outbox` 的 pending 数。SMTP 挂了的时候系统一切正常，只是没人收到通知 |
| 内存持续上涨 | `tokens_in_memory` 是否顶到上限，`radar_events` 是否堆积 |
| 评分突然全体偏低 | 某个端点在静默失败，导致数据完整度整体下滑 |

### 备份

```bash
./radar/scripts/backup.sh              # 备份 + 校验 + 压缩，保留 30 天
./radar/scripts/backup.sh --verify-only
```

用 SQLite 在线备份 API 而不是 `cp`：数据库开着 WAL，写入协程随时在提交事务，直接拷贝会得到一个处于事务中间态的文件——它能打开、能查询，直到真正需要它的那天才发现有一段数据是撕裂的。

每次备份后立即校验并抽查关键表。一个从未被验证过的备份和没有备份没有区别；唯一比"没有备份"更糟的，是"以为有备份"。

建议加进 crontab：

```
0 4 * * * /www/wwwroot/LIQ/radar/scripts/backup.sh >> /www/wwwroot/LIQ/radar/logs/backup.log 2>&1
```

### 回放历史

```bash
.venv/bin/python -m radar.replay \
  --db data/radar.db \
  --config config.yaml \
  --out /tmp/replay.db \
  --start 2026-08-01T00:00:00 --end 2026-08-08T00:00:00
```

改完阈值后，用历史快照重跑一遍，看警报数量和质量的变化。

三条安全边界是硬性的：源库物理只读、邮件走空传输、所有时间取自快照而非墙钟。输出库必须是新文件——不允许覆盖已存在的库，也不允许写回源库。

注意回放窗口如果落进已抽稀的历史区间，CLI 会警告。稀疏数据上跑出来的结果不能当作结论。

## 修改阈值

首选方式是控制台的**配置页**（`/radar/config`）。它由后端参数注册表（`radar/config_schema.py`）驱动，只暴露代码确实会读取的参数，写入前做单值范围与跨字段一致性双层校验（如进入阈值必须高于退出阈值）。启用需在 `radar/.env` 配置：

```bash
echo "RADAR_ADMIN_TOKEN=$(openssl rand -hex 24)" >> radar/.env
```

修改保存在数据卷的 `data/overrides.yaml`（覆盖层），与镜像内的 `config.yaml`（出厂默认）深合并后生效——因此 `deploy.sh` 重建镜像、`git pull` 更新默认值都不会丢掉你的修改。生效方式统一为重启（页面上有一键重启按钮，写队列排空后由 docker 自动拉起，约 20 秒）。

无论走配置页还是直接改 `config.yaml`：

1. `config_hash` 自动变化，新警报会记录新指纹
2. 完整**生效配置**快照写入 `config_audit` 表——半年后仍能回答"当时那套参数是什么"
3. **跨版本的分数不能直接比较**。控制台顶栏常驻显示当前指纹就是为了防止这种比较

凭据永远不进 `config.yaml` 和覆盖层（它们会被完整快照进数据库和导出文件），只走 `radar/.env`。

## 端口暴露前提

雷达 `:8802` 的**只读接口没有应用层鉴权**，与主后端 `:8800` 的姿态一致（管理接口 `/admin/*` 是例外，须携带 `RADAR_ADMIN_TOKEN` 令牌）。这不是疏忽，而是一个前提：

**这两个端口必须由服务器安全组限制来源，只放行你自己的 IP。**

一旦对公网开放，任何人都可以调用 `/api/radar/export/*` 拉走全部研究数据、用 `/api/radar/alerts/{id}/review` 改写复核状态、或反复触发 `/api/radar/research/kpi/rebuild`。CORS 只约束浏览器，对 curl 毫无作用。

凭据本身不会经由接口泄露（`/config` 只返回阈值与指纹，不含 email 段），但数据本身就是这个系统的全部价值。
